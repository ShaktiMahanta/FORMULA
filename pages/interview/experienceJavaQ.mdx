###### `@Transactional`

`@Transactional` is used to manage database transactions in Spring Boot.

- All operations succeed → `Commit`
- Any operation fails → `Rollback`
- Ensures data consistency and integrity.

**Why use it?**

Example: Money Transfer

1. Deduct money from Account A
2. Add money to Account B

If the second operation fails, the first operation is also reverted.

**Basic Syntax**

```java
@Transactional
public void transferMoney() {
    // DB operations
}
```

**Default Rollback**

- `RuntimeException`
- `Error`

```java
@Transactional
public void save() {
    throw new RuntimeException();
}
```

**Rollback for Checked Exception**

```java
@Transactional(rollbackFor = Exception.class)
public void process() throws Exception {
    throw new Exception();
}
```

**Read Only Transaction**

```java
@Transactional(readOnly = true)
public List<User> getUsers() {
    return repository.findAll();
}
```

**Propagation Types**

| Type           | Description                                      |
| -------------- | ------------------------------------------------ |
| `REQUIRED`     | Default. Join existing transaction or create new |
| `REQUIRES_NEW` | Always starts a new transaction                  |

**Interview Points**

- Use in the **Service Layer**.
- Default propagation: `Propagation.REQUIRED`.
- Checked exceptions do not trigger rollback by default.
- Does not work on `private` methods (Spring AOP limitation).

**Quick Remember**

> All Success = Commit
> Any Failure = Rollback

###### `@ControllerAdvice`

`@ControllerAdvice` is used for **global exception handling** across all controllers in a Spring Boot application.

Instead of writing try-catch blocks in every controller, exceptions can be handled in one central place.

**Why use it?**

- Centralized exception handling.
- Cleaner controller code.
- Consistent error responses.
- Reusable across multiple controllers.

**Example**

```java
@RestController
@RequestMapping("/users")
public class UserController {

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        throw new RuntimeException("User not found");
    }
}
```

```java
@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(RuntimeException.class)
    public ResponseEntity<String> handleException(
            RuntimeException ex) {

        return ResponseEntity
                .badRequest()
                .body(ex.getMessage());
    }
}
```

**Common Annotations**

| Annotation              | Purpose                                   |
| ----------------------- | ----------------------------------------- |
| `@ControllerAdvice`     | Global exception handling for controllers |
| `@ExceptionHandler`     | Handles specific exceptions               |
| `@RestControllerAdvice` | `@ControllerAdvice + @ResponseBody`       |

**Using `@RestControllerAdvice`**

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ResponseEntity<String> handleException(
            Exception ex) {

        return ResponseEntity
                .internalServerError()
                .body(ex.getMessage());
    }
}
```

**Interview Points**

- Used for global exception handling.
- Reduces duplicate try-catch blocks.
- Works across all controllers.
- `@RestControllerAdvice` is preferred for REST APIs.
- Commonly used with custom exceptions.

**Quick Remember**

> One application, one global exception handler.

###### `Exception Hierarchy`

Java exceptions follow a hierarchy starting from the `Throwable` class.

```text
Throwable
├── Error
│   ├── OutOfMemoryError
│   └── StackOverflowError
│
└── Exception
    ├── IOException
    ├── SQLException
    ├── ClassNotFoundException
    │
    └── RuntimeException
        ├── NullPointerException
        ├── ArithmeticException
        ├── ArrayIndexOutOfBoundsException
        └── IllegalArgumentException
```

**Types of Exceptions**

| Type                  | Description                             |
| --------------------- | --------------------------------------- |
| `Checked Exception`   | Checked at compile time                 |
| `Unchecked Exception` | Occurs at runtime                       |
| `Error`               | Serious JVM issues, usually not handled |

**Checked Exceptions**

Must be handled using `try-catch` or `throws`.

```java
public void readFile() throws IOException {
}
```

Examples:

- `IOException`
- `SQLException`
- `ClassNotFoundException`

**Unchecked Exceptions**

Occur during runtime.

```java
String str = null;
System.out.println(str.length());
```

Examples:

- `NullPointerException`
- `ArithmeticException`
- `ArrayIndexOutOfBoundsException`

**Errors**

Caused by JVM or system failures.

Examples:

- `OutOfMemoryError`
- `StackOverflowError`

Usually not handled in application code.

**Interview Points**

- `Throwable` is the parent of all exceptions and errors.
- `Exception` represents recoverable conditions.
- `RuntimeException` represents unchecked exceptions.
- Checked exceptions are verified at compile time.
- Errors are generally not recoverable.

**Quick Remember**

> Throwable → Exception & Error → RuntimeException is a child of Exception.

###### `Mapping in Hibernate`

Mapping is the process of connecting Java objects (Entities) with database tables.

Hibernate uses JPA annotations to define relationships between entities.

**Types of Mapping**

| Mapping       | Description                                           |
| ------------- | ----------------------------------------------------- |
| `@OneToOne`   | One record is associated with one record              |
| `@OneToMany`  | One record is associated with multiple records        |
| `@ManyToOne`  | Multiple records are associated with one record       |
| `@ManyToMany` | Multiple records are associated with multiple records |

**One-to-One**

```java
@Entity
public class User {

    @Id
    private Long id;

    @OneToOne
    private Passport passport;
}
```

Example:

- One User → One Passport

**One-to-Many**

```java
@Entity
public class Department {

    @OneToMany(mappedBy = "department")
    private List<Employee> employees;
}
```

Example:

- One Department → Many Employees

**Many-to-One**

```java
@Entity
public class Employee {

    @ManyToOne
    @JoinColumn(name = "department_id")
    private Department department;
}
```

Example:

- Many Employees → One Department

**Many-to-Many**

```java
@Entity
public class Student {

    @ManyToMany
    private List<Course> courses;
}
```

Example:

- Many Students ↔ Many Courses

**Important Annotations**

| Annotation    | Purpose                               |
| ------------- | ------------------------------------- |
| `@Entity`     | Marks a class as a database entity    |
| `@Table`      | Maps entity to a table                |
| `@Id`         | Primary key                           |
| `@JoinColumn` | Foreign key column                    |
| `mappedBy`    | Defines the owning/non-owning side    |
| `@JoinTable`  | Creates a join table for many-to-many |

**Interview Points**

- Hibernate mapping defines relationships between entities.
- `@ManyToOne` is the most commonly used mapping.
- `mappedBy` avoids creating duplicate relationships.
- `@JoinColumn` is used to define foreign keys.
- `@ManyToMany` creates an additional join table.

**Quick Remember**

> OneToOne, OneToMany, ManyToOne, ManyToMany are the four main Hibernate mappings.

###### `Authentication and Authorization in Spring Boot`

**Authentication** = Verifies who the user is.

**Authorization** = Verifies what the user is allowed to access.

Example:

- Login with username/password → Authentication
- Access Admin API only with ADMIN role → Authorization

**Authentication Example**

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public UserDetailsService userDetailsService() {
        UserDetails user = User
                .withUsername("admin")
                .password("{noop}admin123")
                .roles("ADMIN")
                .build();

        return new InMemoryUserDetailsManager(user);
    }
}
```

**Authorization Example**

```java
@Bean
public SecurityFilterChain securityFilterChain(
        HttpSecurity http) throws Exception {

    return http
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/admin/**")
                    .hasRole("ADMIN")
                    .anyRequest()
                    .authenticated())
            .formLogin(Customizer.withDefaults())
            .build();
}
```

**Common Annotations**

| Annotation           | Purpose                         |
| -------------------- | ------------------------------- |
| `@EnableWebSecurity` | Enables Spring Security         |
| `@PreAuthorize`      | Method-level authorization      |
| `@Secured`           | Restricts access based on roles |
| `@RolesAllowed`      | Role-based access control       |

**Method Level Authorization**

```java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
}
```

Only users with `ADMIN` role can access the method.

**Authentication vs Authorization**

| Feature       | Authentication  | Authorization        |
| ------------- | --------------- | -------------------- |
| Meaning       | Verify identity | Verify permissions   |
| Question      | Who are you?    | What can you access? |
| Happens First | Yes             | After Authentication |
| Example       | Login           | Access Admin API     |

**Interview Points**

- Authentication identifies the user.
- Authorization controls access to resources.
- Spring Security handles both authentication and authorization.
- Roles are commonly used for authorization.
- Authentication always happens before authorization.

**Quick Remember**

> Authentication = Who are you?
> Authorization = What are you allowed to do?

###### `Try-With-Resources`

`try-with-resources` is used to automatically close resources such as files, streams, database connections, and scanners after use.

It was introduced in **Java 7**.

**Why use it?**

- Automatically closes resources.
- Prevents resource leaks.
- Cleaner than using `finally` blocks.

**Example**

```java
try (BufferedReader br =
         new BufferedReader(
             new FileReader("test.txt"))) {

    System.out.println(br.readLine());
}
catch (IOException e) {
    e.printStackTrace();
}
```

After execution, `BufferedReader` is automatically closed.

**Without Try-With-Resources**

```java
BufferedReader br = null;

try {
    br = new BufferedReader(
            new FileReader("test.txt"));
}
finally {
    if (br != null) {
        br.close();
    }
}
```

More code and harder to maintain.

**How does it work?**

The resource must implement:

```java
AutoCloseable
```

Examples:

- `BufferedReader`
- `Scanner`
- `FileInputStream`
- `Connection`
- `PreparedStatement`

**Multiple Resources**

```java
try (
    Connection con = dataSource.getConnection();
    PreparedStatement ps =
            con.prepareStatement("SELECT * FROM users")
) {
    // DB operations
}
```

Resources are closed automatically in reverse order.

**Interview Points**

- Introduced in Java 7.
- Automatically closes resources.
- Resource must implement `AutoCloseable`.
- Reduces boilerplate code.
- Preferred over manual closing in `finally`.

**Quick Remember**

> Try-With-Resources = Automatic Resource Closing + No Resource Leaks

###### `Angular Consuming Secured REST Endpoints`

To securely consume a REST API, Angular typically uses **JWT (JSON Web Token) Authentication**.

**Flow**

```text
User Login
    ↓
Angular sends username/password
    ↓
Spring Boot validates user
    ↓
JWT Token generated
    ↓
Angular stores token
    ↓
Angular sends token in API requests
    ↓
Spring Security validates token
    ↓
Response returned
```

**Login Request**

```typescript
this.http.post("/api/auth/login", {
  username: "admin",
  password: "password",
});
```

**Response**

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9..."
}
```

**Store Token**

```typescript
localStorage.setItem("token", response.token);
```

**Send Token in Request**

```typescript
const headers = new HttpHeaders({
  Authorization: `Bearer ${token}`,
});

this.http.get("/api/users", { headers });
```

**Using HTTP Interceptor (Recommended)**

```typescript
@Injectable()
export class AuthInterceptor implements HttpInterceptor {
  intercept(req: HttpRequest<any>, next: HttpHandler) {
    const token = localStorage.getItem("token");

    const clonedReq = req.clone({
      setHeaders: {
        Authorization: `Bearer ${token}`,
      },
    });

    return next.handle(clonedReq);
  }
}
```

Interceptor automatically adds the token to every request.

**Security Best Practices**

| Practice        | Reason                        |
| --------------- | ----------------------------- |
| Use HTTPS       | Encrypts request and response |
| Use JWT Token   | Stateless authentication      |
| Use Interceptor | Avoid duplicate code          |
| Token Expiry    | Prevent misuse of old tokens  |
| Refresh Token   | Generate new access token     |

**Interview Points**

- JWT is the most common approach.
- Angular sends token in `Authorization` header.
- Spring Security validates the token.
- HTTP Interceptor is used to attach tokens automatically.
- Always use HTTPS in production.

**Quick Remember**

> Login → Get JWT → Store Token → Send Bearer Token → Backend Validates → Access Granted

###### `Reverse Proxy`

A Reverse Proxy sits between the client and backend servers.

The client sends requests to the Reverse Proxy, and the proxy forwards them to the appropriate backend service.

**Flow**

```text
Client
   ↓
Reverse Proxy
   ↓
Backend Server
```

**Example**

```text
Client
   ↓
Nginx
   ↓
Spring Boot Application
```

The client never directly accesses the backend server.

**Why Use Reverse Proxy?**

- Hide backend servers.
- Load balancing.
- SSL/TLS termination.
- Security filtering.
- Routing requests to different services.
- Caching responses.

**Nginx Example**

```nginx
server {
    listen 80;

    location / {
        proxy_pass http://localhost:8080;
    }
}
```

Request:

```text
http://myapp.com
```

Forwarded to:

```text
http://localhost:8080
```

**Reverse Proxy vs Forward Proxy**

| Feature  | Reverse Proxy             | Forward Proxy             |
| -------- | ------------------------- | ------------------------- |
| Position | Between client and server | Between user and internet |
| Hides    | Backend servers           | Clients                   |
| Used By  | Server side               | Client side               |
| Example  | Nginx, HAProxy            | Corporate Proxy           |

**Common Reverse Proxy Tools**

- Nginx
- HAProxy
- Apache HTTP Server
- Spring Cloud Gateway
- Kong

**Microservices Usage**

```text
Client
   ↓
API Gateway / Nginx
   ↓
User Service
Order Service
Payment Service
```

The reverse proxy routes requests to the correct microservice.

**Interview Points**

- Reverse Proxy receives requests before backend servers.
- Provides load balancing and security.
- Hides internal server details.
- Commonly used with Nginx and API Gateways.
- Frequently used in Microservices architecture.

**Quick Remember**

> Client → Reverse Proxy → Backend Server → Response

###### `Synchronized`

`synchronized` is used to make a method or block thread-safe by allowing only one thread to access a critical section at a time.

It helps prevent **race conditions** when multiple threads access shared data.

**Why use it?**

Without synchronization:

```text
Thread A → count++
Thread B → count++
```

Both threads may update the same value incorrectly.

With synchronization:

```text
Thread A completes
      ↓
Thread B starts
```

Data remains consistent.

**Synchronized Method**

```java
public synchronized void increment() {
    count++;
}
```

Only one thread can execute the method at a time.

**Synchronized Block**

```java
public void increment() {
    synchronized (this) {
        count++;
    }
}
```

Locks only the critical section instead of the entire method.

**Example**

```java
class Counter {

    private int count = 0;

    public synchronized void increment() {
        count++;
    }
}
```

**Types of Synchronization**

| Type                     | Description                        |
| ------------------------ | ---------------------------------- |
| `Method Level`           | Entire method is locked            |
| `Block Level`            | Only specific code block is locked |
| `Static Synchronization` | Locks class object                 |

**Static Synchronization**

```java
public static synchronized void print() {
}
```

Lock is acquired on the class object.

**Advantages**

- Prevents race conditions.
- Ensures data consistency.
- Makes shared resources thread-safe.

**Disadvantages**

- Performance overhead.
- Threads may wait for lock release.
- Can lead to deadlocks if not used properly.

**Interview Points**

- `synchronized` provides mutual exclusion.
- Only one thread can access the locked resource at a time.
- Uses intrinsic/object lock (monitor lock).
- Method-level synchronization locks the entire method.
- Block-level synchronization is generally preferred for better performance.

**Quick Remember**

> synchronized = One Thread at a Time + Thread Safety

###### `WHERE vs HAVING`

Both `WHERE` and `HAVING` are used to filter data in SQL, but they work at different stages.

**Difference**

| Feature             | WHERE       | HAVING           |
| ------------------- | ----------- | ---------------- |
| Filters             | Rows        | Groups           |
| Used Before         | `GROUP BY`  | After `GROUP BY` |
| Aggregate Functions | Not Allowed | Allowed          |
| Performance         | Faster      | Slower           |

**WHERE Example**

Filter rows before grouping.

```sql
SELECT *
FROM employees
WHERE salary > 50000;
```

Result:

- Only employees with salary greater than 50000 are selected.

**HAVING Example**

Filter groups after aggregation.

```sql
SELECT department_id,
       COUNT(*) AS total_employees
FROM employees
GROUP BY department_id
HAVING COUNT(*) > 5;
```

Result:

- Only departments having more than 5 employees are returned.

**Using WHERE and HAVING Together**

```sql
SELECT department_id,
       COUNT(*) AS total_employees
FROM employees
WHERE salary > 50000
GROUP BY department_id
HAVING COUNT(*) > 5;
```

Execution Order:

```text id="tt8jlwm"
FROM
 ↓
WHERE
 ↓
GROUP BY
 ↓
HAVING
 ↓
SELECT
 ↓
ORDER BY
```

**Interview Points**

- `WHERE` filters individual rows.
- `HAVING` filters grouped/aggregated data.
- `HAVING` is generally used with `GROUP BY`.
- Aggregate functions like `COUNT()`, `SUM()`, `AVG()` are used in `HAVING`.
- Use `WHERE` whenever possible for better performance.

**Quick Remember**

> WHERE filters Rows
> HAVING filters Groups

###### `WHERE and HAVING - Company Example`

Assume we have an `employee` table:

| emp_id | name  | department | salary |
| ------ | ----- | ---------- | ------ |
| 1      | John  | IT         | 80000  |
| 2      | David | IT         | 90000  |
| 3      | Sam   | HR         | 40000  |
| 4      | Alex  | HR         | 60000  |
| 5      | Bob   | IT         | 70000  |

**Using WHERE**

Find employees whose salary is greater than 70000.

```sql
SELECT *
FROM employee
WHERE salary > 70000;
```

Result:

```text
John  - IT - 80000
David - IT - 90000
```

`WHERE` filters individual rows before grouping.

---

**Using HAVING**

Find departments having more than 2 employees.

```sql
SELECT department,
       COUNT(*) AS total_employees
FROM employee
GROUP BY department
HAVING COUNT(*) > 2;
```

Result:

```text
IT - 3
```

`HAVING` filters groups after aggregation.

---

**Using WHERE and HAVING Together**

Find departments having more than 1 employee whose salary is greater than 50000.

```sql
SELECT department,
       COUNT(*) AS total_employees
FROM employee
WHERE salary > 50000
GROUP BY department
HAVING COUNT(*) > 1;
```

Explanation:

- `WHERE salary > 50000` filters employees first.
- `GROUP BY department` groups remaining employees.
- `HAVING COUNT(*) > 1` filters departments.

Result:

```text
IT - 3
HR - 1 (removed by HAVING)
```

**Interview Points**

- `WHERE` filters rows before grouping.
- `HAVING` filters groups after grouping.
- Aggregate functions are used in `HAVING`.
- In real projects, both are commonly used together for reporting queries.

**Quick Remember**

> WHERE → Row Filter
> GROUP BY → Create Groups
> HAVING → Group Filter

###### `OAuth2 Flow`

OAuth2 is an authorization framework that allows users to grant limited access to resources without sharing credentials.

Example:

- Login with Google
- Login with GitHub
- Login with Facebook

**Main Components**

| Component            | Description                        |
| -------------------- | ---------------------------------- |
| Resource Owner       | User                               |
| Client               | Angular/Web/Mobile Application     |
| Authorization Server | Google, Keycloak, Okta, Auth0      |
| Resource Server      | Spring Boot API                    |
| Access Token         | Used to access protected resources |

**OAuth2 Authorization Code Flow**

```text
User
  ↓
Client Application (Angular)
  ↓
Authorization Server (Google/Keycloak)
  ↓
Login & Consent
  ↓
Authorization Code
  ↓
Client Exchanges Code
  ↓
Access Token
  ↓
Call Spring Boot API
  ↓
Resource Server Validates Token
  ↓
Response
```

**Detailed Flow**

```text
1. User clicks Login
      ↓
2. Redirect to Authorization Server
      ↓
3. User enters credentials
      ↓
4. Authorization Code returned
      ↓
5. Client exchanges code for Access Token
      ↓
6. Access Token sent with API requests
      ↓
7. Resource Server validates token
      ↓
8. API response returned
```

**Access Token Usage**

```http
GET /api/users
Authorization: Bearer eyJhbGciOi...
```

**Why Authorization Code Flow?**

- Most secure OAuth2 flow.
- Credentials are never shared with the client application.
- Commonly used in Angular + Spring Boot applications.

**OAuth2 vs JWT**

| Feature          | OAuth2                  | JWT                     |
| ---------------- | ----------------------- | ----------------------- |
| Purpose          | Authorization Framework | Token Format            |
| Token Support    | Can use JWT tokens      | JWT itself is the token |
| Login Providers  | Google, Keycloak, Okta  | Not a provider          |
| Enterprise Usage | Very Common             | Used inside OAuth2      |

**Interview Points**

- OAuth2 is for authorization.
- Authorization Code Flow is the most commonly used flow.
- Access Token is used to access protected APIs.
- Spring Boot APIs act as Resource Servers.
- Keycloak, Okta, Auth0, and Google are common Authorization Servers.

**Quick Remember**

> User Login → Authorization Code → Access Token → API Access

###### `Difference Between save() and persist()`

Both `save()` and `persist()` are used to store entities in the database, but they belong to different APIs and have some behavioral differences.

**Source**

| Method      | Belongs To        |
| ----------- | ----------------- |
| `save()`    | Hibernate Session |
| `persist()` | JPA EntityManager |

**Example**

```java
User user = new User();
user.setName("Shakti");
```

Using `save()`:

```java
session.save(user);
```

Using `persist()`:

```java
entityManager.persist(user);
```

**Differences**

| Feature                    | save()               | persist()    |
| -------------------------- | -------------------- | ------------ |
| API                        | Hibernate            | JPA          |
| Return Type                | Returns generated ID | Returns void |
| Standard                   | Hibernate Specific   | JPA Standard |
| Portability                | Less                 | More         |
| Recommended in Spring Boot | No                   | Yes          |

**save() Example**

```java
Long id = (Long) session.save(user);
```

Returns the generated primary key.

**persist() Example**

```java
entityManager.persist(user);
```

Entity becomes managed by the persistence context.

**Spring Data JPA**

Most projects use:

```java
userRepository.save(user);
```

Internally Spring Data JPA decides whether to:

- Insert a new record
- Update an existing record

**Interview Points**

- `save()` is a Hibernate-specific method.
- `persist()` is a JPA-standard method.
- `save()` returns the generated ID.
- `persist()` returns void.
- In Spring Boot, JPA (`persist`) approach is preferred.
- `JpaRepository.save()` is the most commonly used method in real projects.

**Quick Remember**

> save() → Hibernate Specific + Returns ID
> persist() → JPA Standard + Returns void

###### `Cache Implementation`

Caching is used to store frequently accessed data in memory to reduce database calls and improve application performance.

**Why use Cache?**

Without Cache:

```text
Request
   ↓
Application
   ↓
Database
```

Every request hits the database.

With Cache:

```text
Request
   ↓
Application
   ↓
Cache
   ↓ (Miss)
Database
```

Frequently used data is served from cache.

**Spring Boot Cache Example**

Enable caching:

```java
@SpringBootApplication
@EnableCaching
public class Application {
}
```

Cache a method:

```java
@Cacheable("users")
public User getUser(Long id) {
    return userRepository.findById(id)
            .orElseThrow();
}
```

First Call:

```text
Cache Miss → Database Hit
```

Next Calls:

```text
Cache Hit → Return from Cache
```

**Cache Annotations**

| Annotation       | Purpose                          |
| ---------------- | -------------------------------- |
| `@Cacheable`     | Read from cache, store if absent |
| `@CachePut`      | Update cache                     |
| `@CacheEvict`    | Remove cache entry               |
| `@EnableCaching` | Enable caching                   |

**Cache Eviction**

```java
@CacheEvict(value = "users", key = "#id")
public void deleteUser(Long id) {
}
```

Removes stale data from cache.

**Popular Cache Providers**

- Redis
- EhCache
- Caffeine
- Hazelcast

**Real-Time Example**

```text
Product Details
User Profile
Configuration Data
Master Data
```

These are commonly cached because they change infrequently.

**Interview Points**

- Cache improves performance by reducing database calls.
- First request is usually a Cache Miss.
- Subsequent requests are Cache Hits.
- Redis is the most commonly used distributed cache.
- Cache invalidation is important to avoid stale data.

**Quick Remember**

> Cache Hit → Fast Response
> Cache Miss → Database Call → Store in Cache

###### `Cache Types - Local vs Global Cache`

Caching can be implemented as **Local Cache** or **Global (Distributed) Cache**.

**Local Cache**

- Cache is stored inside the application memory (JVM).
- Each application instance maintains its own cache.
- Very fast access.
- Cache is lost when the application restarts.

```text
App Instance 1
      ↓
 Local Cache

App Instance 2
      ↓
 Local Cache
```

Examples:

- Caffeine
- EhCache (Local Mode)

**Global (Distributed) Cache**

- Cache is stored in a separate cache server.
- Multiple application instances share the same cache.
- Suitable for Microservices and distributed systems.

```text
App 1 ──┐
        │
App 2 ──┼── Redis Cache
        │
App 3 ──┘
```

Examples:

- Redis
- Hazelcast
- Memcached

**Comparison**

| Feature        | Local Cache              | Global Cache               |
| -------------- | ------------------------ | -------------------------- |
| Storage        | Application Memory (JVM) | External Cache Server      |
| Sharing        | Not Shared               | Shared Across Applications |
| Performance    | Faster                   | Slight Network Overhead    |
| Scalability    | Limited                  | Highly Scalable            |
| Restart Impact | Cache Lost               | Cache Remains Available    |
| Microservices  | Not Preferred            | Preferred                  |

**Real-Time Usage**

| Scenario                       | Cache Type           |
| ------------------------------ | -------------------- |
| Single Spring Boot Application | Local Cache          |
| Multiple Microservices         | Global Cache (Redis) |
| Frequently Read Data           | Both                 |
| Distributed Systems            | Global Cache         |

**Interview Points**

- Local cache resides in JVM memory.
- Global cache is shared across multiple services.
- Redis is the most popular distributed cache.
- Local cache is faster but not shared.
- Global cache ensures consistency across instances.

**Quick Remember**

> Local Cache = Inside Application (JVM)
> Global Cache = Shared Cache Server (Redis)

###### `Dialect and hibernate.ddl-auto`

**Dialect**

Hibernate Dialect tells Hibernate which database is being used and how to generate database-specific SQL queries.

Examples:

```properties
spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect
```

```properties
spring.jpa.database-platform=org.hibernate.dialect.MySQLDialect
```

Why needed?

- SQL syntax differs across databases.
- Hibernate generates optimized SQL based on the selected dialect.

Examples:

- PostgreSQLDialect
- MySQLDialect
- OracleDialect
- SQLServerDialect

**hibernate.ddl-auto**

Controls how Hibernate handles database schema creation and updates.

```properties
spring.jpa.hibernate.ddl-auto=update
```

**Values**

| Value         | Description                         |
| ------------- | ----------------------------------- |
| `none`        | No schema changes                   |
| `validate`    | Validate schema against entities    |
| `update`      | Update schema without deleting data |
| `create`      | Drop and recreate schema on startup |
| `create-drop` | Create on startup, drop on shutdown |

**Examples**

```properties
spring.jpa.hibernate.ddl-auto=validate
```

Checks if tables and columns match entity definitions.

```properties
spring.jpa.hibernate.ddl-auto=update
```

Adds missing tables/columns automatically.

```properties
spring.jpa.hibernate.ddl-auto=create
```

Recreates all tables every startup.

**Recommended Usage**

| Environment               | ddl-auto             |
| ------------------------- | -------------------- |
| Local Development         | `update`             |
| QA/UAT                    | `validate`           |
| Production                | `validate` or `none` |
| Flyway/Liquibase Projects | `validate`           |

**Interview Points**

- Dialect helps Hibernate generate database-specific SQL.
- `ddl-auto` controls schema generation behavior.
- `update` is useful during development.
- Avoid `create` and `create-drop` in production.
- In production, schema changes are usually managed by Flyway or Liquibase.

**Quick Remember**

> Dialect = Which Database?
> ddl-auto = How Hibernate Manages Schema?

###### `Database Connection Pool and HikariCP`

A Connection Pool maintains a pool of reusable database connections instead of creating a new connection for every request.

**Why use Connection Pool?**

Without Pool:

```text
Request
   ↓
Create DB Connection
   ↓
Execute Query
   ↓
Close Connection
```

Creating connections repeatedly is expensive.

With Pool:

```text
Request
   ↓
Get Connection from Pool
   ↓
Execute Query
   ↓
Return Connection to Pool
```

Improves performance and scalability.

**What is HikariCP?**

- Default connection pool in Spring Boot.
- High-performance JDBC connection pool.
- Fast, lightweight, and production-ready.

**Spring Boot Configuration**

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/testdb
spring.datasource.username=postgres
spring.datasource.password=admin

spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.minimum-idle=5
spring.datasource.hikari.connection-timeout=30000
```

**Important Properties**

| Property             | Description                            |
| -------------------- | -------------------------------------- |
| `maximum-pool-size`  | Maximum connections in pool            |
| `minimum-idle`       | Minimum idle connections               |
| `connection-timeout` | Wait time before timeout               |
| `idle-timeout`       | Time before idle connection is removed |
| `max-lifetime`       | Maximum lifetime of a connection       |

**Connection Flow**

```text
Application
      ↓
HikariCP Pool
      ↓
Database
```

**Benefits**

- Faster database access.
- Reuses connections.
- Reduces database overhead.
- Handles concurrent requests efficiently.

**Interview Points**

- HikariCP is the default connection pool in Spring Boot.
- Connections are reused instead of recreated.
- Pool size should be configured based on application load.
- Too many connections can overload the database.
- Connection pooling improves performance and scalability.

**Quick Remember**

> Without Pool → Create Connection Every Time
> With HikariCP → Reuse Existing Connections

###### `HashMap vs ConcurrentHashMap`

Both are used to store data as **key-value pairs**, but they differ in thread safety.

**HashMap**

- Not thread-safe.
- Multiple threads can cause data inconsistency.
- Faster in single-threaded applications.
- Allows one `null` key and multiple `null` values.

```java
Map<Integer, String> map = new HashMap<>();
map.put(1, "Java");
```

**ConcurrentHashMap**

- Thread-safe.
- Supports concurrent read and write operations.
- Uses internal locking mechanisms for better performance.
- Does not allow `null` key or `null` value.

```java
Map<Integer, String> map =
        new ConcurrentHashMap<>();
map.put(1, "Java");
```

**Comparison**

| Feature         | HashMap                | ConcurrentHashMap             |
| --------------- | ---------------------- | ----------------------------- |
| Thread Safe     | No                     | Yes                           |
| Performance     | Faster (Single Thread) | Better for Multi-Threading    |
| Null Key        | 1 Allowed              | Not Allowed                   |
| Null Value      | Multiple Allowed       | Not Allowed                   |
| Synchronization | None                   | Internal Concurrent Mechanism |
| Use Case        | Single Thread          | Multi-Threaded Applications   |

**Internal Working**

```text id="lzm1pk"
HashMap
  ↓
Array
  ↓
Bucket
  ↓
LinkedList / Tree
```

```text id="w7tjlwm"
ConcurrentHashMap
  ↓
Multiple Threads
  ↓
Concurrent Access
  ↓
Thread-Safe Operations
```

**When to Use?**

- `HashMap` → Single-threaded applications.
- `ConcurrentHashMap` → Multi-threaded applications, caches, shared data structures.

**Interview Points**

- HashMap is not thread-safe.
- ConcurrentHashMap is thread-safe.
- ConcurrentHashMap performs better than synchronized HashMap in concurrent environments.
- ConcurrentHashMap does not allow null keys or values.
- Both provide O(1) average lookup time.

**Quick Remember**

> HashMap = Fast but Not Thread Safe
> ConcurrentHashMap = Thread Safe for Concurrent Access
